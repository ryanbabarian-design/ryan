# 제안관리 웹시스템 V1 설계

## 목표

종이 또는 엑셀 기반의 제안 접수와 접수현황 전사를 하나의 공개형 웹화면으로 통합하고, 관리자의 심사 작업만 인증 계정으로 제한한다.

## 확정 요구사항

- 직원은 로그인 없이 제안을 제출한다.
- 신규 제안은 제출 즉시 공개된다.
- 제안자 이름, 부서, 상세내용, 개선 전·후 사진, 심사결과, 점수, 포상금, 효과금액을 전체 공개한다.
- 직원은 기존 제안을 검색하여 중복·유사 제안을 확인한다.
- 직원명은 직원명단에서 선택하고 부서는 자동입력한다.
- 직원명단은 관리자가 Excel로 일괄 업로드하고 이후 갱신한다.
- 제안자는 접수번호와 4자리 수정번호로 수정한다.
- 관리자가 상태를 심사중 또는 심사완료로 바꾸면 제안자 수정은 잠긴다.
- 관리자는 개인 이메일·비밀번호로 로그인한다.
- 관리자는 심사, 점수, 포상, 실시, 지급, 삭제를 수행한다.
- 기존 2026년 접수현황을 이관한다.

## 구조

GitHub Pages는 정적 화면을 제공한다. 데이터, 관리자 인증, 사진 저장은 Supabase Database, Auth, Storage가 담당한다. 동일 화면이 설정값에 따라 브라우저 localStorage 데모 저장소 또는 Supabase 저장소를 사용한다.

## 공개 데이터 흐름

1. 공개 화면에서 직원명 선택과 제안 입력
2. 사진 Storage 업로드
3. 서버 함수가 동시성 안전한 접수번호 발급
4. 제안 DB 저장
5. 접수현황과 통합검색에서 즉시 조회

## 수정 흐름

1. 제안자가 상세화면에서 수정 선택
2. 접수번호와 4자리 수정번호 제출
3. DB 함수가 수정번호 해시와 잠금상태 검증
4. 미심사 제안만 수정
5. 심사중·심사완료는 관리자만 수정

## 관리자 흐름

1. Supabase 이메일·비밀번호 인증
2. admins 테이블에서 관리자 권한 확인
3. RLS가 관리자에게만 쓰기 권한 부여
4. 심사상태 변경 시 잠금값 갱신
5. 점수 기준 포상금 계산 및 저장

## 보안 경계

- 브라우저에는 publishable/anon key만 사용한다.
- service_role key는 브라우저에 저장하지 않는다.
- 공개 읽기는 요구사항에 따라 허용한다.
- 익명 등록과 수정은 제한된 SECURITY DEFINER 함수로 처리한다.
- 관리자 직접 수정·삭제는 Auth와 RLS로 제한한다.
- 사진은 공개 버킷에 저장하되 업로드 확장자와 파일크기를 제한한다.
